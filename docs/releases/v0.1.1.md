# M365 MCP Server v0.1.1

This patch release adds draft-file attachments to the remote MCP server and the
Windows x64 single executable. It retains the MIT License, delegated `/me`
mailbox boundary, and draft-first send policy from v0.1.0.

## Draft attachments

- `mail_add_draft_attachment` attaches one file of 1 byte to 20 MiB to an
  existing draft without sending it. Files below 3 MB use Graph's direct
  attachment API; larger files use a sequential upload session.
- Remote clients can stage raw bytes with a delegated Bearer token at
  `POST /uploads/attachments` and pass the short-lived, user-bound handle to
  the MCP tool. In OAuth mode, `mail_prepare_attachment_push` can instead issue
  a five-minute, one-use grant bound to the user, draft, filename, MIME type,
  byte length, and SHA-256. A local client pushes raw bytes to `/uploads/push`
  with that grant; the subsequent MCP call attaches the staged file. These
  process-memory grants require the same server worker throughout the flow.
- The Windows EXE supports `inspect-attachment` and `push-attachment` commands
  for a remote connector. They read only a file beneath the configured
  `M365_ATTACHMENT_ROOT` and push to a fixed HTTPS
  `M365_ATTACHMENT_PUSH_URL`; no browser upload, Base64 through MCP, or OAuth
  token handoff is required.
- In Windows-local stdio mode, the same EXE accepts
  `mail_add_draft_attachment(draft_id, relative_path)` and attaches directly
  through the locally signed-in user's Graph session. The path must resolve
  inside `M365_ATTACHMENT_ROOT` and identify a non-empty DOCX, XLSX, PPTX,
  ZIP, or PDF of at most 20 MiB. Omitting `relative_path` retains the native
  file picker for interactive use. Neither mode writes a temporary attachment
  file.

Creating or attaching to a draft does not authorize sending. Interactive sends
require separate confirmation; bounded automation remains a client/agent
authorization responsibility. An ambiguous send or attachment outcome must
be checked before retrying.

## Distribution

The release workflow publishes the tested Linux x64 image as
`ghcr.io/sagehou/m365-mcp-server:v0.1.1`, `:0.1.1`, `:0.1`, and `:latest`.
It also attaches the exact Windows x64 NativeAOT single executable
`m365-mcp-windows-x64.exe`, its `.sha256` checksum, and the MIT `LICENSE` to
the GitHub Release. GitHub Artifact Attestation records build provenance for
that executable. The executable requires no Python or .NET runtime on the
target PC.

The Windows executable is not Authenticode-signed. The live Release description
includes MD5 and SHA-1 for exact-file antivirus allowlisting; these legacy
hashes are not authenticity proofs. Verify SHA-256 and the GitHub attestation
for provenance. Any new binary requires a new allowlist review.

## Boundaries

- Local file-path automation requires an operator-configured artifact root.
  The EXE constrains its own file access; a WorkBuddy Bash tool used with a
  remote connector has broader permissions and needs client-side sandbox and
  approval policy.
- Transient upload grants and staged bytes are held in bounded process memory,
  not shared across server workers or preserved through restart.
- The release remains Outlook Mail-focused; it does not add Calendar,
  OneDrive, SharePoint, Teams, HTML composition, shared-mailbox access, or
  server-enforced automation-send policy.
