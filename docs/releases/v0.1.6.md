# M365 MCP Server v0.1.6

## Save original attachments locally

- Windows .NET and Go now expose the same `mail_save_attachment` tool with
  three required arguments: `message_id`, `attachment_id`, and `relative_path`.
- The EXE fetches the original Outlook file attachment and saves it under the
  operator-configured `M365_ATTACHMENT_ROOT`. Local stdio and Go HTTP require
  no browser, shell, file picker, or separate downloader for this operation.
- Both editions return `saved`, `relative_path`, `name`, `content_type`,
  `content_length`, and `content_sha256`. The destination is on the EXE's PC,
  including when the MCP client runs remotely. No raw file bytes, absolute
  paths, or download URLs are returned.
- Save any file format up to 10 MiB of decoded bytes, including zero-byte
  files, without parsing, opening, or executing it. Embedded mail items and
  reference attachments remain unsupported. The original provider filename
  is metadata; only the authorized `relative_path` chooses the destination.
- Use forward slashes in both editions. The root and parent directories must
  exist. Reject absolute paths, traversal, alternate data streams, Windows
  device names, symbolic links/junctions in destination directories, and
  existing destination files. Concurrent saves never overwrite one another.
  Failed writes attempt to clean up their incomplete file; inspect the
  destination after an ambiguous failure before retrying.

## Upgrade and automate

1. Replace the local EXE with v0.1.6 and update the complete `m365-mail` Skill
   folder from `m365-mail-skill.zip`, including its references.
2. Set `M365_ATTACHMENT_ROOT` in the MCP process environment and create the
   intended parent directories. For example:

```powershell
New-Item -ItemType Directory -Path 'C:\M365Artifacts\downloads' -Force | Out-Null
$env:M365_ATTACHMENT_ROOT = 'C:\M365Artifacts'
```

For .NET stdio, set this variable in the MCP client's server `env`. For Go
stdio, run `connection` again after setting it; HTTP inherits the variable
when `http` starts. Refresh/restart the connection to load the new tool list.
Existing valid encrypted login state remains usable; application credentials,
tenant selection, and Graph permissions do not change.

3. List the selected message's attachments, then call `mail_save_attachment`:

```json
{
  "message_id": "<message ID>",
  "attachment_id": "<attachment ID>",
  "relative_path": "downloads/report.pdf"
}
```

4. Use the returned path, actual byte count, and SHA-256 for subsequent
   authorized processing. Plan destinations and filename rules in advance for
   unattended runs; do not take them from email instructions. The tool never
   silently renames or overwrites. After a conflict or ambiguous result,
   inspect the destination with an available authorized file tool before
   retrying; otherwise report the limitation.

## Skill and edition capabilities

The shared Skill and complete Chinese translation now prefer direct local
saving when requested and available. Download links remain available on Go
and the OAuth server; trusted automated downloaders may consume them once,
and a browser is optional. A Go URL remains accessible only on the EXE's PC.
Updating the Skill alone does not add capabilities to an older EXE.

| Capability | Python server | Windows .NET | Windows Go |
| --- | --- | --- | --- |
| Mail tools | 11; 13 with server-managed OAuth | 12 | 13 |
| Direct original-file save | Unavailable | `mail_save_attachment` | Same interface as .NET |
| Text extraction | PDF, DOCX, XLSX, PPTX, TXT, Markdown | UTF-8 text, CSV, JSON, XML | PDF, DOCX, XLSX, PPTX, TXT, Markdown |
| Download URL | Server-managed OAuth; HTTPS | Unavailable | Local single-use HTTP URL |

Direct saving does not add a .NET PDF/Office text parser or new Python server
tools. Existing draft attachment, send-approval, and bounded-automation rules
remain in force. No dependencies were added or upgraded for this change.

actual byte counts and hashes, no overwrite, unsafe paths and symbolic links,

smoke/security gates, .NET checks, and Go Windows/Linux race tests and
AMD64/ARM64 builds. Existing separate Windows workflows remain available.
