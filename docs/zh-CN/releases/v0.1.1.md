# M365 MCP Server v0.1.1

本次补丁版为远端 MCP Server 和 Windows x64 单文件 EXE 增加草稿文件附件能力，
沿用 v0.1.0 的 MIT 许可证、委托 `/me` 邮箱边界及先创建草稿再发送的策略。

## 草稿附件

- `mail_add_draft_attachment` 可为现有草稿添加单个 1 字节至 20 MiB 的文件，
  不会发送邮件。小于 3 MB 使用 Graph 直接添加，更大文件使用顺序上传会话。
- 远端客户端可使用 Delegated Bearer Token 向 `POST /uploads/attachments`
  推送原始字节，再把短时、用户绑定的句柄传给 MCP 工具。OAuth 模式下，也可通过
  `mail_prepare_attachment_push` 签发五分钟、一次性的上传凭据，绑定用户、
  草稿、文件名、MIME 类型、字节数及 SHA-256。本机客户端携带凭据向
  `/uploads/push` 推送原始字节，后续 MCP 调用再添加附件。进程内凭据要求整个
  流程命中同一个 Server Worker。
- Windows EXE 为远端 Connector 提供 `inspect-attachment` 和
  `push-attachment` 命令。它们只读取配置的 `M365_ATTACHMENT_ROOT` 下文件，
  并推送到固定 HTTPS `M365_ATTACHMENT_PUSH_URL`；不需要浏览器上传、经 MCP
  传输 Base64 或向本机命令交付 OAuth Token。
- Windows 本地 stdio 模式下，同一 EXE 接受
  `mail_add_draft_attachment(draft_id, relative_path)`，通过本地登录用户的
  Graph 会话直接添加附件。相对路径最终必须仍位于 `M365_ATTACHMENT_ROOT`
  内，文件须是非空且不超过 20 MiB 的 DOCX、XLSX、PPTX、ZIP 或 PDF。
  不传 `relative_path` 时保留交互式原生文件选择框。两种模式均不写临时附件文件。

创建草稿或添加附件不构成发送授权。交互发送仍需单独确认；受限自动发送仍由
Client/Agent 层实施授权。发送或附件添加结果不明确时，重试前须先核对状态。

## 分发

Release Workflow 将通过测试的 Linux x64 镜像发布为
`ghcr.io/sagehou/m365-mcp-server:v0.1.1`、`:0.1.1`、`:0.1` 和 `:latest`。
GitHub Release 还会附上精确构建的 Windows x64 NativeAOT 单文件
`m365-mcp-windows-x64.exe`、其 `.sha256` 校验文件和 MIT `LICENSE`。
GitHub Artifact Attestation 记录该 EXE 的构建来源；目标电脑无需安装 Python
或 .NET Runtime。

Windows EXE 没有 Authenticode 签名。正式 Release 说明会提供精确文件的 MD5
和 SHA-1，供兼容旧式杀毒白名单表单；它们不能证明文件真实性。请用 SHA-256
和 GitHub Attestation 核验来源。二进制文件改变后须重新审核白名单。

## 边界

- 本地路径自动化需要管理员配置产物根目录。EXE 只限制自身的文件访问；远端
  Connector 使用的 WorkBuddy Bash 工具权限更广，还需客户端沙箱和审批策略。
- 临时上传凭据与文件字节保存在有容量上限的进程内存中，不跨 Server Worker
  共享，重启后失效。
- 本版仍聚焦 Outlook Mail；不增加 Calendar、OneDrive、SharePoint、Teams、
  HTML 撰写、共享邮箱访问或由 Server 强制执行的自动发送授权策略。

配置及上限见[工具契约](../tool-spec.md)、[Windows 指南](../windows-local.md)和
[部署指南](../deployment.md)。
